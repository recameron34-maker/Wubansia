# Spec: drums on one track for MIDI drags (ADR 0025, v0.2)

- **Asked by the user** (Ableton Live 12 and Logic Pro on macOS), verbatim: "when dragging full song midi's I'd like an
  option to input the drum midis as a single drum rack midi".
- **Branch:** `drumrack` from d06bc70. Worktree: `the repo root`.
  Its `libs/` is a copy: never run `git submodule update` there. A release build is already in `build/release`.
- **Status:** proposed. The user can still change the choices in section 12.
- **Line numbers** below are at d06bc70. The worktree's own `CLAUDE.md` is the current one and applies in full.
- **Updated 2026-11-14:** ADR 0025 is the record of what was built; these points changed since this spec, and are edited
  in place. The review fixes (2026-11-13): a phrase title that won't fit its chip even squeezed to 0.8 drops its bar
  count, and the strip's label slot and divider gap give the chips their slack (section 6.3); `dist/INSTALL.md` gives
  every kit's drum pads in a table, and says that a Song dropped in Live writes over the tracks after it, with drops
  that don't, so the ROADMAP's check and `docs/listening.md` ask for the drop in a new set or project (section 7). The
  merge with the Samples drawer (2026-11-14): the settings seam and save helper were folded into the drawer's
  (sections 6.1, 6.2 and 10).

## 0. The decision in one paragraph

The drag strip gets a switch, **1 drum track**. It is off by default and kept for the person in `settings.xml`, never in
the project and never as a parameter. When it's lit, a **Loop** or **Song** drag gives its drum tracks (Kick, Rumble,
Snare, Clap, Snare/Clap, Hats, Perc) as **one track named `Drums`**:
- on channel 10, with every note exactly as it was;
- where the first drum track was, which is right after the conductor in every kit file.

The conductor, the header (but its track count) and every other track stay byte for byte. A new core function,
`midi::mergeTracks`, writes the merged track through the existing SMF writer, so it is deterministic and keeps
note-offs first on a tick.

Lane and phrase drags don't change. When fewer than two drum tracks are left after mutes, the drag is exactly today's
file. There is no new parameter, no state change, no new dependency, and no change to `content/midi` except a line in
four READMEs.

## 1. Which drags change

| Drag | With the switch lit | Why |
|---|---|---|
| Song (extended mix) | Drums on one track | It's what the user asked for. |
| Loop | Drums on one track | Same files, same code path and same switch. It's the other whole-kit drag. |
| Lane (a lane's MIDI chip) | Unchanged | A lane is already one track, except FUT04's kick lane (Kick + Rumble). Its rumble needs its own gated pad anyway, and changing it would rename that kit's lane files. |
| Phrase | Unchanged | Phrase files hold no drums. |
| A new "Drums" chip (drums only) | Not added | The strip has no room (ADR 0024). Lighting the switch and muting the six other lanes already gives conductor + `Drums` from Loop or Song. |
| `content/midi`, region files, `EmbeddedContent` | Unchanged | The merge runs at drag time on the embedded bytes. Region files are never dragged. |

If **fewer than two drum tracks are kept** (mutes), the drag is the switch-off drag: same name, same bytes. There is
nothing to merge, the lone drum track already comes first after the conductor, and one name stays one file.

## 2. The merged track

- **Which tracks merge.** The drag's kept tracks whose name has the drums role in `engine/kit/channel_map.h`'s
  `kTracks` (channels.py's TRACKS): Kick, Rumble, Snare, Clap, Snare/Clap, Hats, Perc.
  - Never Accents, FX, Vox chops or a kit's extras (channels 11-16), whatever their lane.
  - Muted lanes' tracks are already out before the merge.
  - Write the check as a local helper in `DragFiles.cpp` that scans `kTracks` for `ChannelRole::drums`. `channel_map.h`
    itself doesn't change.
- **Name: `Drums`.** It is not added to TRACKS or `kTracks`: it spans four lanes and no content file carries it, so
  ADR 0019's map stays as it is. `trackLane` gives it -1, and nothing reads drag output.
- **Channel 10, as the notes already are.** Every drum track uses channel 10 only (status 0x99/0x89). Nothing is
  re-channelled.
- **Notes unchanged:** key, tick, length, velocity and release velocity.
  - The keys stay the kit map's: 36 kick, 37 rim, 38 clap or snare, 42 and 46 hats, 51 ride, percussion per the kit
    README, and FUT04's rumble on 35.
  - There is no GM remap: the FUT01 and FUT03 clap stays on 38 (ADR 0019 owns the map).
- **Place:** the slot of the first merged track. That is track 1, right after the conductor, in all 16 Loop and Song
  files, so a drop onto a Drum Rack or Drum Machine Designer track puts the drums there.
- **Order: the writer's** (`core/midi/writer.h`).
  - On one tick: the name, text events, note-offs, program changes, controllers, note-ons; then by channel, then key.
  - Every status byte is written (no running status).
  - The track ends on the latest end tick among the merged tracks, which is the conductor's: 15360 or 860160.
  - This keeps the "note-offs first on a tick" rule (`docs/midi-map.md:55`) wherever one drum track's note-off meets
    another's note-on. That happens on 103 ticks in FUT02's Song, 419 in FUT03's Song, 90 in FUT04's Song and 2 in
    FUT04's Loop. Interleaving the tracks in file order would break the rule there.
- **Determinism.** The merge is integer-only with stable sorts and depends only on the embedded bytes, so every platform
  gets the same bytes.
- **Key clashes.** None exist: in all 137 `content/midi` files, no key appears in two drum tracks of one file.
  - Same-key notes from two tracks still merge, as long as they don't overlap.
  - The writer refuses an overlap, two values of one controller or two program changes on one channel and tick, the
    same text twice on a tick, and a zero-length note. Then the drag fails and the chip shows "Couldn't write".
  - The tests prove all 16 files merge, so a future kit that breaks this fails CI, not a user's drag.
- **CC, program changes and text.** None of the 137 files has any of these on its drum tracks, no CC on channel 10
  anywhere, and no channel-10 event outside the drum tracks.
  - The merge carries controllers, program changes and text events (FF 01-0F) anyway. Each merged track's own name
    (FF 03) is dropped.
  - It **refuses** what it can't carry as it is:
    - pitch bend, key or channel pressure, sysex;
    - any other meta event (tempo, signatures, SMPTE, port, sequencer-specific);
    - a note-on with no note-off before its track ends, and a note-off with no note to end.
  - A note-on with velocity 0 used as a note-off comes out as 0x8n with velocity 0. None of the content has one.
- **Size:** the file gets slightly smaller (FUT01 Song Vox: 119,242 → 116,834 bytes).

**Checked on the content.** Script: `<scratch>/drumspec-verify/check.py`,
with a reader and writer model in `smf.py` next to it.
- In all 16 Loop and Song files, the drum tracks:
  - are tracks 1-4 (FUT04: 1-5), back to back after the conductor;
  - are format 1 at 960 PPQ;
  - hold only FF 03 and notes, all on channel 10, with note-off velocity 0 and no running status;
  - have no zero-length or unended notes, and end on the conductor's tick.
- A simulated merge gives the same notes, keeps every other chunk byte for byte, and parses.
- Each drum chunk is identical between Vox and NoVox, and equal to `<KIT>_Drums_4bars.mid`.

|---|---|---|
| FUT01 | Kick 36; Clap 38; Hats 42, 46; Perc 37, 47, 54 | all 120 |

## 3. Core: `midi::mergeTracks` (`core/midi/track_select.{h,cpp}`)

Add this beside `keepTracks`, with a sentence in the file's header comment ("... and merging some of them into one
track"):

```cpp
// keepTracks (smf, trackIndices), but with the tracks at mergeIndices (kept too) written as one track named name, in
// the place of the first of them in file order: their notes, controllers, program changes and text events, each
// track's own name left out, laid out by toFile () (writer.h): on a tick the name, text events, note-offs, program
// changes, controllers, note-ons, then channel and key; every status byte explicit; ending on the latest end tick
// among them. The header (track count rewritten), the conductor and every other kept track are copied byte for byte.
// Fails, saying why, where keepTracks fails; when mergeIndices names fewer than two distinct tracks, or track 0; when
// a track to merge holds what can't be carried as it is (pitch bend, key or channel pressure, sysex, a meta event
// other than a text event, a note-on with no note-off before its track ends, a note-off with nothing to end); and
// where toFile () refuses the merged track (overlapping notes on one channel and key, two values of one controller or
// two program changes on one channel and tick, the same text twice on a tick, a note-off on its note-on's tick).
[[nodiscard]] util::Result<std::vector<std::uint8_t>> mergeTracks (std::span<const std::uint8_t> smf,
    std::span<const int> trackIndices, std::span<const int> mergeIndices, std::string_view name);
```

How to build it:
1. Get `layoutOf (smf)` and check the indices as `keepTracks` does. Also refuse track 0 in `mergeIndices`, or fewer than
   two distinct merge tracks.
2. Scan each merge track's events in ascending index order.
   - Refuse the unsupported kinds listed above.
   - Pair notes with one counter per channel and key, to catch an unended note-on or a stray note-off.
   - Gather `notesOf`, `controllersOf` and `programsOf` into one `TrackSpec`, and `textsOf` without type 0x03.
   - Set `endTick` to the largest end tick.
3. Write the track: `toFile (SongSpec { ppq = file.ppq, endTick, tracks = { spec } })`, take `tracks[1]`, then
   `encode (File { 1, ppq, { that track } })`. The chunk is the bytes after `encode`'s 14-byte MThd.
   `writer.{h,cpp}` stay as they are, which also leaves the generator snapshots alone.
4. Assemble the output:
   - the source header, with the count set to the kept tracks minus (merged tracks - 1);
   - then, in file order: the new chunk at the first merge index, and every other kept chunk copied as it is.
5. Start error messages with "can't merge tracks 1, 2, 3, 4: ". The writer's own text follows; it numbers channels
   from 0.

## 5. File names

The name is `<KIT> <Title> <BPM> <Key> <Camelot> - <Loop|Song>[ NoVox][ (<marks>)].mid`.

The marks are "1 drum track" when the drums merged, then "no <muted lane labels>", joined by ", ". With the switch off,
or with at most one drum track left, the names are exactly today's.
- `FUT01 Alloy Signal 134 F#m 11A - Song (1 drum track).mid`
- `FUT01 Alloy Signal 134 F#m 11A - Song NoVox (1 drum track, no Clap, Warp Bass).mid`
- `FUT04 Furnace Code 136 Em 9A - Loop (1 drum track, no Anvil).mid`
- `FUT02 Orbit Relay 130 Dm 7A - Song (no Kick, Clap, Hats).mid`: only Zap is left, so this is the plain file.

Different bytes get different names, and one name is one file: DragOutTests' enumeration checks this, with the
switch-on drags added. Every name above, the switch text and the tooltips pass `tools/sound/denylist.py check`. The
longest name stays far under `kMaxStem` (196), and the cache rules (32 newest) don't change.

## 6. The setting, the Controller and the switch

### 6.1 `UserSettings` (per user, `settings.xml`)

- **Attribute:** `drag_drums_one_track="1"` on the root when the switch is on. It's removed when off. Anything else, a
  missing file or another root tag reads as off.
- **API**, with comments in the file's style:
  - `bool dragDrumsOnOneTrack() const;` reads the file once, as `contentFolder ()` does.
  - `bool setDragDrumsOnOneTrack (bool on);` writes at once and keeps every other attribute. It returns false when the
    file can't be written; the choice still holds until the process ends.
  - It does **not** bump `generation ()`, because the content folders don't change.
- **Private helper:** `bool saveAttributeLocked (const char* attribute, const juce::String& value) const`, where an
  empty value removes the attribute. It is the "keep whatever else the file holds" code that `setContentFolder` holds
  inline. (Since the merge with the Samples drawer, one `saveLocked (attribute, value)` serves every setter: section 10.)
- **Still lazy.** Nothing reads the file at construction (`StateTests.cpp:501-510`). `PluginEditor`'s first `tick ()`
  reads it, as the editor opens; that is fine and matches what hosts do.
- **One file per process.** One instance is shared by every plugin instance and the Standalone app in the process.
  Another running process picks up a change when it next starts, as with the content folder.

## 8. Tests first

Following the repo's pattern: one commit with the tests, the declarations they need and stubs, so everything builds and
the new tests fail. Then the implementation.

- **`core/tests/test_track_select.cpp`:**
  - **Hand-made files**, built chunk by chunk like the existing ones:
    - **Order:** two drum tracks with notes on shared ticks, where an off from A meets an on from B at tick 120. The
      expected MTrk bytes are spelled out: name, then offs by key, then ons by key.
    - **Placement:** the merged track sits at the first merge index, other kept tracks and the conductor stay byte for
      byte, and the header count is rewritten.
    - **End:** the end tick is the maximum (A ends at 3840, B at 4000, so 4000).
    - **Order of indices:** reversed `mergeIndices` give the same bytes, and merge tracks count as kept.
    - **Running status** in a source track is accepted. A note-on with velocity 0 comes out as 0x8n with velocity 0.
    - **Carried:** CC and program change on channel 10 at distinct ticks, and an FF 01 text, all in the writer's order.
      The FF 03 names are dropped.
  - **Refusals, each with its message:**
    - overlapping same-key notes from two tracks;
