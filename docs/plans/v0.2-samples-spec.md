# Samples: browse, hear and drag Wubansia's sounds into your DAW (v0.2, ADR 0024)

This is the final spec. It merges the three designs (producer, safety, minimal) with the four maps. Paths are relative to the repo root (the spec was written at d06bc70, before the code; ADR 0024 records what the code settled).

**Updated 2026-11-14.** The drawer's review fixes (2026-11-13 and 14, merged as e335bb1) and the integration's (9ded392 to ffefea8) changed what this spec says on these points, now edited in place: decision 1's footprint; `replaceWithData` and the checked write (§2.2, decision 18, §5.4); the default file's "Why" (decision 8); a clip given up after 300 ms without a block, and each host's no-sound words (decision 13, §3.4, §4.3, §4.4); export names without a leading "Accent " (decision 17, §5.2); the drag's `externalDragPath` and the reveal without a shell (decision 19, §4.5); the hidden lanes, a loop's part, the keyboard and Esc, what screen readers hear, and the banner and failure lines (§3); the files and the API (§4.1, §4.2); `readFile` as `FileSampleSource::readBytes`; the samples folder's refusals (§5.1); the folder's size (§5.4, §8); the tests (§6) and CI's Xvfb step (§6.2); the `#` and copy-time risks (§8). The editor sketch's drag strip also shows ADR 0025's 1 drum track switch. ADR 0024 is the record of what the code settled. The three defaults of §8's questions were announced to you and await your OK.

---

## 1. Summary

**What you get**
- **The Samples button opens a browser.** The **Samples** button at the top right of Wubansia used to show where the samples are installed. It now opens a **Samples drawer** over the lanes and the FX row. The kit cards, the display, the transport and the MIDI drag strip stay where they are, and the groove keeps playing.
- **Sounds sorted into groups.** The drawer lists every sound of the kit in seven groups: **Accents** first, then FX, Vox, Synths, Bass, Drums and Loops.
  - FUT01 Alloy Signal has 35 sounds, FUT02 Orbit Relay 37, FUT03 Glass Current 36 and FUT04 Furnace Code 32.
  - Four kit chips let you look through another kit's sounds without changing what plays.
- **Click a sound to hear it.** It plays dry, exactly as the file you will get, on top of whatever is playing. ↑ and ↓ step through the list and play each sound. ■ or Esc stops.
- **Drag a sound into your DAW.** Drag the row, or the big tile, into Live or Logic.
  - You get the kit's own 48 kHz / 24-bit WAV, byte for byte.
  - Its name tells you what it is, for example `Rave Stab v2 - FUT01 134 F#m 11A.wav`.
  - It is saved in `~/Music/Wubansia/Samples/FUT01 Alloy Signal/`. Wubansia never cleans that folder up, so your projects keep finding their files.
- **Every recorded take is reachable.** The File box lists every recorded note, velocity layer and round robin of the sound.
- **Tips tell you how to place it.** For example: "ends on the beat", "starts 25 ms before its beat", "2 bars at 134 BPM".
- **Clicking the tile shows the file in Finder.** Use this if your host refuses drops. It is also the keyboard path.
- **Your project doesn't change.** There is no new parameter and nothing new in its saved state.

**Not in v0.2** (§9):
- renders "as heard in the kit", with its Space and Echo;
- favourites and search;
- auditions in time with the groove;
- dragging several files at once;
- root-note and tempo tags inside the WAV.

## 2. Decisions

### 2.1 Scores (1-10)

| Criterion | D1 producer | D2 safety | D3 minimal |
|---|---|---|---|
| (a) Meets both asks | **9**: all kits, variants, multi-file drag | 8: all kits, one file per drag | 7: current kit only |
| (b) Producer UX in Live 12 and Logic | **8**: richest, but its toggle is hidden in a full strip | 7: the "Preparing…" drag only starts once the mouse moves again | 6: kit-first names truncate on Drum Rack pads |
| (c) Real-time and file safety | 7: more moving parts (synced starts, Kit FX, a WAV writer) | **9**: tickets, retire-once accounting, offline stays bit-identical | 5: a clip pins a whole Kit; the audio thread reads a clock |
| (d) Fits the codebase and the WebView | 6: sidecar pipeline, CMake and `KitSource` changes | **8**: JUCE-free `engine/audition`, Controller API | 7: small API, but clip freeing is tied to editor polling |
| (e) Testability | 7 | **9**: fault injection, race and accounting tests | 8 |
| (f) Scope discipline | 3: pulls most of M6 forward | 6: heavy custom file-system layer | **9** |
| **Total (of 60)** | 40 | **47** | 42 |

**The verdict**
- The final spec is D2's engine and real-time core.
- It ships D3's scope and entry point.
- It takes D1's producer touches that cost little: browsing all four kits, sound-first names and a folder you can change.

### 2.2 Corrections to the designs (checked in the code)

**The drag strip has no room for a Sounds toggle (D1, D2).**
- `DragStrip::resized` gives the phrase chips the 740 px left after the label, Loop and Song (`editor/DragChip.cpp:162-180`).
- FUT01's five phrase files already fill it: (740 − 4 × 6) / 5 = 143 px each, under the 176 px cap. FUT02-FUT04 leave 18 px.

**CI has no TSan job (D2; D1 implies one).**
- `.github/workflows/ci.yml` runs only `ctest --preset release`, on Linux, macOS and Windows.
- v0.1's TSan run was local (`docs/ROADMAP.md:146`). §6 gives the local command.

**`ContentSourceFactory::open (…)->read (path)` returns decoded audio (D2).** It can't be checked against kit.json's SHA-256, so this spec adds a call that returns bytes (decision 20).

**JUCE's temporary file and rename make a write atomic (D2).**
- `File::replaceWithData` writes a hidden temporary file, then renames it into place (`libs/JUCE/modules/juce_core/files/juce_File.cpp:777-786`, `juce_TemporaryFile.cpp:94-119`).
- It ignores a failed write, though, and would rename a short file into place. So `exportCopy` writes the same hidden `TemporaryFile` itself, unbuffered, checks the write and the file's size, and only then renames it (ADR 0024, "Settled in the code (step 1)").
- D2's platform renames (`renamex_np`, `renameat2`, `MoveFileExW`), its fsyncs and its free-space checks still aren't needed.

**D3's clip can keep an old kit in memory.**
- D3's clip holds a `shared_ptr<const Kit>`, and only the message thread frees clips, through `collect ()` from `audition`, `auditionState` or `prepareToPlay`.
- With the editor closed after a kit switch, a retired clip keeps the old Kit (50-90 MB) alive.
- D3's audio thread also reads `steady_clock` to drop stale requests.

**FUT04 has 32 sounds, not 33 (D3).** Accent Metal Chord Em is one file set in two lanes (ch 12 `chords` and ch 6 `accents`). It is shown once, in Accents.

**Kit-first names truncate badly (D3).** With names like `FUT01 Alloy Signal 134 F#m 11A - Rave Stab v2.wav`, every Drum Rack pad and Simpler reads "FUT01 Alloy Sig…".

**The sidecar isn't needed (D1).**
- Every count, default file and length comes from kit.json.
- Only the pitches of FUT01's and FUT02's one-key accents live in the recipes alone (for example `ROOT3 = 54`, F#3, in `tools/sound/recipes/fut01/accents.py:35`). The export names don't need them (§9).

**`engine/` allows no JUCE at all, despite CLAUDE.md's layout line.**
- CLAUDE.md says "JUCE dsp is allowed" under `engine/`.
- `engine/tests/rules.cmake` fails any JUCE include, any `juce::`, and even the words `addFrom`, `applyGain`, `AudioBlock` and `FloatVectorOperations` anywhere under `engine/`, comments included (ADR 0017).
- So the audition code that goes into `engine/audition/` must be plain C++ and must never use those words.

**The synthetic kit's "ready" folder is empty (all three).**
- All three test plans assume WAVs in it, but `SyntheticContent::locate` names an empty temp path and serves the audio from memory (`plugin/tests/helpers/synthetic_content.h`, `folderOf`, `Source::read`).
- The synthetic WAV bytes do match its manifest's SHA-256 (`engine/testing/synthetic_kit.cpp:417`), so `readFile` (decision 20) can serve them.

**Content facts that hold** (checked under `p13/real-samples`, and the editor's size):
- All 618 installed files match kit.json's SHA-256.
- They hold only `fmt ` and `data` chunks.
- The installed file names are unique per kit, ignoring case, and use safe characters only. The longest export name is 46 characters.
- EditorTests pins the editor at 1120 × 700 × zoom (`plugin/tests/EditorTests.cpp:206-207`, `822-823`, `839`).

### 2.3 Decisions

**Scope and entry**
1. **Ship this as v0.2, ahead of S1b2, under ADR 0024.**
   - Why: you asked for it, and ADR 0017 set the precedent for pulling work forward.
   - It touches `plugin/`, `engine/audition/`, `engine/kit/`'s `FileSampleSource` (`readBytes`, decision 20) and the engine's tests of both, `README.md`, `dist/INSTALL.md` and docs, a test of `dist/INSTALL.md` in `tools/content/tests`, and CI's Linux job (the drawer's keyboard-focus case under Xvfb, §6.2). S1b2's PR #6 (the core generator; ADR 0023 is on `pr6-int`) carries on untouched.
2. **The header's Samples button opens the drawer.** This is D3's choice, over D1/D2's new drag-strip button.
   - Why: it's your word for the feature, in the most visible place, and the drag strip has no room (§2.2).
   - The install panel stays reachable through the drawer's "Content…" button, and it still opens by itself when the current kit's samples are missing.
3. **The drawer sits over the lanes, A/B and FX.** It is (20, 246), 1080 × 396, inside the zoomed `content` component, and the editor stays 1120 × 700. All three designs agree. The lanes, A/B and FX are hidden while it shows, so Tab and screen readers never reach a control under it.
   - Why: no layout change and no failing size checks. The header, display, transport, section strip and MIDI drag strip stay usable.
4. **Browse all four kits; play one sound at a time.** This follows D1/D2, over D3's current kit only.
   - Why: auditions and copies read the installed files directly. Another kit costs nothing to browse, and nothing in the project changes.

**Catalog**

5. **Build the catalog in C++ from the embedded kit.json alone.** This follows D2/D3, over D1's `*_sounds.json` sidecar.
   - Why: the manifests already hold everything needed.
   - A sidecar would add a Python generator, a CMake glob and a way to drift, all for one fact (§9).
6. **One sound per distinct instrument file set.**
   - Instruments that share their files merge into the most "flair" category of the two (D2).
   - Each phrase stem is a Loop.
   - Why: FUT02's two Glass Pings, FUT04's three accent twins and FUT01's Glitch Fill Lift Beat 4 aren't different sounds.
7. **Seven categories: Accents, FX, Vox, Synths (the lead and chords lanes), Bass, Drums, Loops.**
   - Why: on their own, Lead holds 1-2 sounds per kit and Chords 1-3.
8. **The default file and the File box.**
   - The default is the top velocity layer's first round robin.
   - For a pitched instrument, it comes from the lowest zone rooted on the kit's tonic, or from the middle zone if none is.
   - A File box (D3), not D1's chips, reaches every file.
   - Why: the default is the kit's key note in the lowest register that has one, at its loudest. That is usually a note the kit's loops play, but not for three sounds: FUT03's Vox Synth and Keys EP give G3, below the G4 up the kit plays them, and FUT02's Chrome Arp gives D4, below its arp's A4-C6 (SoundCatalogTests pins them). One combo box handles 1 to 18 files with a widget the LookAndFeel already styles.

**Audition**

9. **Auditions are a dry clip player, summed after the engine and before master_gain.** All three designs agree.
   - Why: you hear exactly what you will drop.
   - Routing through the kit would add lane mutes, groove ducks, sends and the A/B switch, would be cut by host CC120 and CC123, and would be faded by kit swaps.
10. **Clips own their audio and are made on a sound thread, one per processor.**
    - The player and the clip maker live in `engine/audition/`. They are JUCE-free and resample with the voices' `SincBank`.
    - This is D2's design. It rejects D3's clip that holds a Kit.
    - Why: nothing in the audition path touches Kit lifetimes, `KitCache` or the engine's kit retire FIFO, and the engine's rules apply and are checked.
11. **The real-time protocol.**
    - Clips go in through a `PendingSlot` (latest wins) and come back through a `RetireFifo` of 8.
    - Stops are tickets: `stopUpTo (ticket)`. A `sounding ()` atomic reports the ticket playing.
    - Why: a stop can't miss a clip in flight, every clip comes back exactly once, and the audio thread never frees anything.
12. **Offline renders and bypassed blocks never play an audition, and an idle player touches nothing.**
    - Why: a bounce is bit-identical with or without a click.
    - RenderTests' bit-for-bit comparison of the processor with `groovecore` still holds. Adding 0.0f would turn −0.0 into +0.0.
13. **A host that runs no audio gets a hint, not a stale click.**
    - The sound thread withdraws an offer that no block took within 300 ms. This uses D2/D3's 300 ms, not D1's 250 ms. A clip a block took is given up the same way once no block has come for 300 ms (the host stopped mid-clip): the first block back lets it go unheard, without even a fade.
    - The drawer then says why there's no sound: Logic's hint in Logic only; in any other host "No sound from your DAW: it isn't running Wubansia's audio right now. Check that its audio engine is on and this track is active."; in the Standalone app, its own audio settings (§3.4).
    - Why: Logic runs a stopped instrument track only while it's selected or armed. Withdrawing means no stale click plays when you later press Play, with no clock on the audio thread.
14. **The level is a fixed −6 dB, then master_gain.** The sound starts at once, with no bar sync, as in D2/D3.
    - Why: scope. Auditions in time with the groove are M6.

**Export**

15. **The exported file is the installed file, byte for byte.** It is checked against kit.json's size and SHA-256, and gets no `smpl` or `acid` chunks. This follows D2/D3, over D1.
    - Why: it is provably the kit's audio, and all 618 installed files pass that check here.
    - Neither DAW is shown to need the chunks, and the names carry the note, tempo and key.
16. **The folder is `<Music>/Wubansia/Samples/<KIT> <Title>/`.** It is flat, you can change it, and Wubansia never trims or deletes it.
    - This takes D1/D2's Change… over D3's fixed folder, and a flat folder over D1's category subfolders.
    - Why: Live and Logic reference dropped audio where it sits.
    - Flat means one file has one path even when it shows in two categories. FUT02's `Laser Chord Stab D4 v2` is both the Accents "Laser Chord Stab Dm9" and the Synths "Laser Chord Stab" default.
17. **Names are `<installed file name> - <KIT> <BPM> <Key> <Camelot>[ c<N>].wav`, frozen once released.**
    - The sound comes first (D1/D2). The installed name is used (D3), less a leading "Accent ", as the drawer's names drop it: FUT03's and FUT04's 18 accent files give `Dub Chord Cm9 - FUT03 128 Gm 6A.wav`, not `Accent Dub Chord Cm9 - …`. ` c<N>` is added from content v2 on (D2).
    - Why: drum pads and Simpler show the start of a name.
    - The installed names are already unique per kit (618 checked), safe, and carry the note, the layer and the round robin; they stay unique without "Accent ".
18. **Copies are written only where no file of that name exists.**
    - `exportCopy` writes a hidden temporary file whole and unbuffered, checks its size, then renames it into place. JUCE's `replaceWithData` would rename a part-written file (§2.2).
    - A file of that name with the same bytes is reused untouched. One with other bytes gets the next name: `(2)`, `(3)`… up to `(999)`. So does a dangling link at the name, which is left as it is.
    - Nothing is ever overwritten or deleted. This follows D1/D3, over D2's platform-specific code.
    - Why: the rename makes each write atomic, and names follow content, so a rival instance writes the same bytes.
19. **The drag copies synchronously inside `mouseDrag`, then calls `performExternalDragDropOfFiles ({file}, false, &source)` with no callback.** The file goes as `dragout::externalDragPath` gives it: the path on macOS and Windows, a percent-encoded `file://` URL on Linux. A click on the tile copies and reveals the file (`dragout::revealToUser`: on Linux, xdg-open on its folder, never through a shell). One file per drag. This follows D1/D3 and DragChip, over D2's asynchronous "Preparing…".
    - Why: macOS needs the current mouse event (`juce_Windowing_mac.mm:192-238`).
    - The worst case is FUT03's 4.3 MB 8-bar riser: its copy took 18-24 ms on the Linux build machine (BenchmarkTests' budget is 100 ms); its SHA-256 alone took 14 ms here.
    - D2's way only starts the drag at the next mouse move once the file is ready.
20. **`ContentSourceFactory::readFile (found, path)` returns a listed file's bytes.** This takes D2's idea, but with bytes instead of decoded audio. The installed content reads them with `FileSampleSource::readBytes`, the engine's own read without the decode (§4.2).
    - Why: auditions and copies then run in tests on the synthetic kit with no files on disk, and the SHA-256 check needs bytes.

**State and API**

21. **No new state.**
    - No parameter and no state attribute; ADR 0018 is untouched. The selection is UI-only, like the zoom.
    - The samples folder is per user, in `settings.xml` as `samples_folder`, and setting it doesn't bump the content generation.
    - Why: browsing never marks your project changed.
22. **The Controller gains seven calls:** `sounds`, `audition`, `stopAudition`, `auditionState`, `exportSound`, `samplesFolder` and `setSamplesFolder`.
    - The drawer is a native panel behind them. S1f's WebView calls the same and keeps a native drag tile.
    - Why: JavaScript can't start an OS file drag.

### 3.3 Interactions

| You do | You get |
|---|---|
| Click **Samples** | The drawer opens on the playing kit, at the last category used, Accents on first open, and its list takes the keyboard. The install panel closes. Click again, or ×, to close it; closing stops the audition. |
| Click a kit chip | Browses that kit. The playing kit and the project don't change. |
| Click a category | Shows its sounds and selects the first one, without playing it. |
| Mouse-down on a row | Selects the row and plays its chosen file from the top. It restarts if it was playing; the replaced sound fades out over 5 ms. |
| Click ■ (row or header), or press Esc | Stops, with a 5 ms fade, and puts the status line away. Esc is taken only when there is something to stop or put away; otherwise it reaches the host. |
| ↑ / ↓, while the list has focus | Selects the previous or next row and plays it. |
| Return | Plays the selected row again. |
| Pick a file in **File** | Plays it. From then on, the drag, the tile and Show in Finder use it for this sound, while the editor is open. |
| Drag a row or the tile 4 px | Copies the file into the samples folder if it isn't there, then starts the OS drag. Drop it in Live, Logic or Finder. |
| Click the tile, or **Show in Finder** | Copies the file if needed and shows it. |
| **Change…** | Opens a folder chooser. The folder is kept for you, never in projects. |
| **Content…** | Closes the drawer and opens the install panel. |
| Click a kit card (select a kit) | The drawer follows the new kit, unless you picked a chip. The audition stops. |
| Space, ⌘ shortcuts, any other key | Never handled; they reach the host. |

**Accessibility**
- Each row's title reads like "Rave Stab, 0.71 seconds": its name, a loop's part ("Context Vox Riff, vox loop, 6 bars, …"), its length, and what its hint says of the grid, whichever row is selected (", ends on the beat", ", starts 20 ms before its beat", ", a 4-bar loop, then a 2-bar echo tail"). Its press action plays the sound.
- Chips and categories are titles, not toggles (a toggle's press action would untick them): "FUT01 Alloy Signal, shown, playing", "Accents, 3 sounds, shown".
- The tile's title is its visible words and the file ("Drag into your DAW: …", "Couldn't save …"); its help is the detail pane's hint, then what a press does. Its press action copies the file and shows it: the keyboard path to a file.
- Each new status line and banner is announced once, a failed copy's or audition's detail with it; the banner's button carries the banner.
- Focus order: chips, categories, rows, File, tile, Play, Show in Finder.

### 3.4 States

| State of the browsed kit or the request | Rows | Banner or status line |

    {
    public:
        static constexpr std::size_t kRetireSlots = 8;
        static constexpr float kGain = 0.5f;           // -6 dB, before the plugin's master_gain
        static constexpr double kFadeSeconds = 0.005;  // a replaced or stopped clip

        ~AuditionPlayer(); // deletes every clip it still holds (offered, playing, fading, retired); audio stopped

        void prepare (double sampleRate) noexcept;     // message thread, audio stopped
        double rate() const noexcept;                  // any thread: what clips are made for; 0 before prepare

        template <class F> void collectRetired (F&& f) noexcept; // f (const AuditionClip*) per clip let go

        // Audio thread. Adds the playing clip x kGain into out[0..numOutputs); 1 output gets (L + R) / 2.
        // silent (an offline render, a bypassed block) writes nothing and lets every clip go unplayed.
        // With nothing playing it touches nothing.
        void process (float* const* out, int numOutputs, int numSamples, bool silent) noexcept;
        void reset() noexcept;                         // audio thread (the host's reset): every clip let go now

        std::uint32_t sounding() const noexcept;       // any thread: the ticket playing (not fading out), 0 when none
        bool offered() const noexcept;                 // any thread: an offer waits for the audio thread

        // Any thread: the blocks process () has run, silent ones too; the sound thread watches it for a host that
        // has stopped running blocks.
        std::uint64_t blocksRun() const noexcept;
        // The sound thread, once no block has come for a while: if the next block is the first since `seen` blocks
        // had run, the clips in hand (never the offer) go at its start, unplayed and unfaded; if a block ran
        // meanwhile, nothing changes.
        void dropIfIdleSince (std::uint64_t seen) noexcept;

    private:
        // One clip in the audio thread's hands: its position, its fade-out once stopped or replaced, and whether it
        // ended (or faded out) while `retired` was full, held silent until there's room.
        struct Slot { const AuditionClip* clip = nullptr; std::int64_t position = 0; int fadeLength = 0, fadeLeft = 0; bool done = false; };

        PendingSlot<AuditionClip> pending;
        RetireFifo<AuditionClip, kRetireSlots> retired;
        std::atomic<double> rate_ { 0.0 };
        std::atomic<std::uint32_t> stopTicket { 0 }, soundingTicket { 0 };
        std::atomic<std::uint64_t> blocks { 0 }, dropAt { 0 };
        Slot current; // the clip playing, which fades out where it is once stopped
        Slot fading;  // the clip it replaced, fading out

### 4.3 Threads and what they share

| Thread | Does | Shares, and how |
|---|---|---|
| Message | Editor; Controller calls; `exportSound`'s file I/O (synchronous, at most about 25 ms); `prepare` | With the sound thread: a request slot and status, under a mutex. With the audio thread: `stopUpTo` (atomic). |
| Sound ("Wubansia sounds", one per processor) | `readFile`; SHA-256; `engine::readWav` (`engine/kit/wav_reader.h`); `makeAuditionClip`; `offer`. While the player holds a clip of its, every 50 ms it drains retired clips, withdraws an offer left untaken for 300 ms, and gives up the clips a block took once no block has come for 300 ms (`checkHeld`, which reads the offer, the playing ticket, then the block count); with nothing out, it sleeps until the next request. It deletes clips. | With the audio thread: `PendingSlot<AuditionClip>` in, `RetireFifo<AuditionClip, 8>` out, and the `rate_`, `sounding`, block count (`blocksRun`) and drop (`dropIfIdleSince`) atomics. |
| Audio | `AuditionPlayer::process` and `reset`, from `processBlock` (steps 2 and 7b) and `processBlockBypassed` | Atomics and the two lock-free queues only. It never allocates, frees, locks, logs, does I/O or throws. |

**Ownership.**
- Every clip is created with `new` on the sound thread. It comes back exactly once: from `offer`'s return, from `collectRetired`, or to `~AuditionPlayer` at teardown.
- Whoever gets it back deletes it, and that is never the audio thread.
- No clip refers to a Kit.

**Adoption rule on the audio thread.**
- At the start of each block, the clips in hand go unplayed and unfaded if the sound thread gave them up (`dropIfIdleSince`) and no block ran since it looked.
- A pending clip is taken only while no replaced clip is still fading out and `retired` has room.
- A clip that has ended, or finished fading, while the FIFO was full is held silently and retried at the next block. Nothing is adopted until the FIFO has room.
- A clip whose `rate` differs from `rate_` is let go unplayed.
- So is any clip whose ticket is `<= stopTicket`; a playing one fades out where it plays, from the next block's first sample.

### 4.4 Data flow: audition

1. **The row.** A mouse-down on a row makes `SamplesPanel` call `controller.audition ({ "FUT01", 166 })` (166 is `Music/Rave Stab v2.wav` in FUT01's kit.json).
2. **`ControllerImpl::audition`**, on the message thread:
   - It finds the catalog entry and the `FileEntry`.
   - It finds where the kit is: the current kit through `status ()`, any other through `kitService ().kitStatus (entry->index)`, which the idle survey fills (`KitService.cpp:334-375`).
   - Unless the state is `ready` with a folder, it returns 0 and hands the reason to `SoundService::refuse ()`: what plays stops, as the new sound would have replaced it, and the reason is `auditionState ().problem`.
   - Otherwise it returns `processor.sounds->audition ({ kit, contentVersion, found, file })`.
3. **The sound thread** takes the latest request, then:
   - reads the bytes with `content.readFile (found, file.path)`;
   - refuses them unless the size and `util::sha256Hex (bytes)` (`core/util/sha256.h:14`) match kit.json;
   - decodes them with `engine::readWav (bytes)`;
   - checks the frames and channels;
   - makes the clip with `engine::makeAuditionClip (data, player.rate () > 0 ? player.rate () : 48000, ticket)`.
   - If a newer request or a stop came in meanwhile, it deletes the clip. Otherwise it calls `delete player.offer (clip)`, which deletes any older offer that was never taken.
   - A file that fails a step is refused as a copy of it would be (`sounds::unreadableSource`, `sounds::mismatchedSource`): the problem names the file in the kit, never its folder or a check's code, `detail` keeps the reader's words, `sourceProblem` and `reinstall` say what helps, and what played stops.
4. **The audio thread**, at the next `processBlock`:
   - Step 7b takes the clip at sample 0 of the block.
   - The playing clip, if any, fades out over 5 ms.
   - The new clip is added × 0.5 into the buffer; master_gain follows in step 8.
   - At its end the clip goes to `retired`.
5. **The sound thread, every 50 ms while the player holds a clip of its:**
   - It deletes retired clips.
   - If the offer is still untaken after 300 ms, `player.offer (nullptr)` takes it back. The thread deletes it and sets `hostSilent`.
   - If a block took a clip but no block has come for 300 ms (`checkHeld`: the offer, the playing ticket, then the block count), it stops the playing ticket and calls `player.dropIfIdleSince (blocks)`, so the next block lets the clips in hand go unheard; `hostSilent` is set when that was the latest.
6. **The editor, on each 30 Hz tick:** `auditionState ()` drives the row's ■, its "…" and the status line: the no-sound hint for the host (§3.4) or a failure's line.
7. **Stops.** `stopAudition`, closing the drawer, `selectKit` (even of the kit already playing; an unknown id stops nothing) and closing the editor with the drawer open all call `SoundService::stop ()`. That records `stoppedUpTo = latest`, calls `player.stopUpTo (latest)` at once, drops the queued request, and wakes the thread to withdraw any offer.

### 4.5 Data flow: drag

1. **Starting the drag.** On a row or the tile, `mouseDrag` reaching 4 px from the press (DragChip's threshold, `DragChip.cpp:64-71`) calls `controller.exportSound (ref)`.
2. **`ControllerImpl::exportSound`** resolves the kit as in §4.4, then returns `sounds::exportCopy (*processor.content, found, entry->info, file, samplesFolder ())` (§5.4).
3. **On success**, the hook `startDrag (file, component)` runs. By default that is `editor::startExternalDrag`, which calls `juce::DragAndDropContainer::performExternalDragDropOfFiles ({ dragout::externalDragPath (file) }, false, &component)`:
   - It runs inside the mouse event, and returns as soon as the OS drag begins (on every OS in JUCE 9.0.4).
   - The file goes as its path on macOS and Windows, and as its percent-encoded `file://` URL on Linux, where JUCE would otherwise write the bare path into the drop and targets cut it at `#`.
   - `false` means copy (`NSDragOperationCopy`).
   - There is no completion callback, and nothing is ever deleted after the drop.
4. **On failure**, no drag starts. The tile turns the warning colour and the footer shows the failure's line (§3.4, "Export failed").
5. **A click without a drag** on the tile, or **Show in Finder**, runs `exportSound`, then `revealFile (file)`, by default `dragout::revealToUser`: on Linux, xdg-open on the file's folder, started by a middle child that exits at once, never through a shell (where `$`, backticks and quotes in a folder's name would act); elsewhere `File::revealToUser`.

### 4.6 Catalog rules (`sounds::soundsOf`)

1. **Instruments, in manifest order.**
   - Each instrument's file set is every round-robin file index over its zones and layers.
   - If an earlier sound has the same set, the instrument merges into it. The earlier sound keeps its id, name and place in the list.
   - The merged sound takes the higher category in the order Accents > FX > Vox > Synths > Bass > Drums.
   - If the newcomer is pitched and the earlier one isn't, the newcomer's zones choose the default file.
2. **Category by lane.**
   - `accents` is Accents; `fx` is FX; `vox` is Vox.
   - `lead` and `chords` are Synths; `bass` is Bass.
   - `kick`, `snare`, `hats` and `perc` are Drums.
3. **Then each phrase stem**, in phrase order (stem a, then b), becomes a Loop, unless it is already a sound. `loopBars` is `cycle_16ths / 16`. A loop's `part` is its phrase's lane as a category (a bass line's is Bass); every other sound's `part` is its category.
4. **`files`**: zones in order, each zone's layers soft to hard, each layer's round robins; a file seen before is skipped.
5. **`defaultFile`**:
   - Pitched means any zone has `lo < hi`.
   - A pitched instrument uses the first zone whose `root % 12` is the tonic, else `zones[size / 2]`.
   - A one-key instrument uses `zones[0]`.
   - The default is that zone's last layer's first round robin.
   - The tonic is the first word of `kit.key` ("F#", "D", "Bb") as a pitch class.
6. **`name`** is the instrument name with a leading "Accent " dropped. A loop's name is its file name without folder and ".wav". `id` is `"<KIT>/<instrument id>"` or `"<KIT>/<path>"`.
7. **`bars`**:
   - `bars = round (frames / framesPerBar)` when that is at least 1 and within 48 frames (1 ms) of whole bars; otherwise 0.
   - `framesPerBar = 48000 × 240 / bpm`.
   - `leadInMs = round (preroll_frames / 48)`; `endAligned = align == end`.

### 5.3 Bytes and metadata

- **The bytes are exactly the installed file:** RIFF/WAVE with `fmt ` (PCM, 24-bit, 48 kHz, mono or stereo) and `data`.
  - All 618 installed files hold only these two chunks and match kit.json's SHA-256 (checked in `p13/real-samples`).
  - Nothing is decoded, re-encoded, resampled, trimmed or tagged. The 48 kHz / 24-bit masters stay masters, as CLAUDE.md's content rules ask.
- **No `smpl`, `acid` or `LIST` chunks** (§9). The facts a producer needs are in the name and the exact length:
  - note, layer and round robin, from the kit's own file names;
  - the kit, tempo, key and Camelot code;
  - whole bars for loops and risers.
- **Before anything is written,** the bytes are refused unless their size equals what kit.json implies and their SHA-256 equals kit.json's `sha256`.
  - The message reads, for example: "Rave Stab v2.wav isn't the file FUT01's content v1 lists: reinstall FUT01".
  - A file that can't be read is refused by the reader's error code, never its words or folder: "FUT04's Stems/Acid Line 1 Clean 4 Bars.wav is missing", or "... can't be read" (§3.4).

### 5.4 Idempotence and never-delete (`exportCopy`)

```
target = folder/<KIT> <Title>/<name>.wav
for k in 1, 2, 3 ... 999:                  # name, then "<name> (2)", "<name> (3)" ... "<name> (999)"
    if nothing is at target, not even a dangling link:
        create the folder
        write the bytes whole to a hidden TemporaryFile beside it, unbuffered; check the write and its size
        rename it to target                # replaceWithData would rename a part-written file
        return target, or the problem
    if target holds these bytes exactly (size, then a byte compare): return target   # nothing written
    # another file, or a dangling link, holds the name (edited in a DAW, say): never touched; try the next name
every name taken: the problem "every name for it is taken in the samples folder"
```

**Guarantees**
- **Idempotent:** the second drag of a sound writes nothing; its mtime stays the same.
- **Never overwrites:** an edited copy keeps its edits, and projects that use it keep working.
- **Never deletes.** This module has no delete call. JUCE's `TemporaryFile` removes only its own temporary file, and only on a failed write.
- **No half-written file:** the write is checked before the rename, which makes each write atomic.
- **Names follow content, so concurrent writers agree.** Two instances exporting the same sound write the same bytes, so a race between them leaves one correct file.
- **Uninstalling leaves the folder in place.** INSTALL.md's "Uninstall" says so.

**Sizes**
- One file is at most 4.3 MB (the 8-bar risers).
- Exporting everything in all four kits comes to 618 files and 204.5 MB per content version, plus one more file (`(2)`, `(3)`…, up to `(999)` for a name) each time a sound whose copy was edited in place is dragged again. Tidying the folder is your call.

## 8. Risks, what can't be verified here, questions

### Risks

1. **Drops from a plugin window are unverified in both DAWs.**
   - Even v0.1's "Drag MIDI" box is still unticked (`docs/listening.md:152`).
   - Reports to know about:
     - A JUCE VST3 drop into Live has raised an error dialog.
     - Logic 11.2 changed which drops it accepts. It reportedly takes plain file URLs, which is what JUCE sends (`juce_Windowing_mac.mm:192-238`).
     - Logic may run the AU out of process on Apple Silicon.
   - **Fallback:** Show in Finder, which works whatever the host.
   - **Early check you can do today:** v0.1's Drag MIDI chips use the same call. Try them in Live 12 (VST3 and AU) and in Logic before step 3 lands.
2. **Logic is silent for a stopped, unselected track.** Logic runs a stopped instrument track only while it's selected or armed, and "Only load plug-ins needed for project playback" can keep the plugin idle. The hint appears after 300 ms.
3. **Writing `~/Music` from Logic's AU host process is unverified.**
   - It's expected to work:
     - `~/Music` isn't on the published privacy-protected list.
     - v0.1 already reads `~/Library/Application Support` from Logic, so it isn't in a sandbox container. That is an inference.
   - **Change…** is the way out.
4. **`#` in names (F#m, F#4) is unverified inside Live and Logic.** Through drag URLs it is settled: macOS makes the file URL itself, Windows hands paths over, and on Linux the drawer gives JUCE each file's percent-encoded `file://` URL (`dragout::externalDragPath`). Names freeze at release, so the check in each DAW comes before release (v0.2's checklist asks for a FUT01 sample in Live and in Logic). The fallback rule (sharps spelled "s") is a one-line change, safe only before release.
5. **Logic projects at 44.1 kHz.** A 48 kHz file plays at the wrong speed unless sample-rate conversion on import is on. INSTALL.md says so.
6. **The synchronous copy at drag start.** The worst case, FUT03's 4.3 MB riser, took 18-24 ms on the Linux build machine (its SHA-256 alone took 14 ms here). A slow external drive could stall longer; BenchmarkTests watches it (budget 100 ms).
7. **Auditions have no limiter.** Over a loud groove they can pass 0 dBFS. That is float inside the DAW, so nothing clips before the master.
8. **Keys reaching the plugin window differ by host.** Only ↑ ↓ Return Esc are handled, and only while the list has focus.
9. **The export folder only grows,** by design: 205 MB per content version if every file is taken once, plus one more file (`(2)`, `(3)`…, up to `(999)` for a name) each time a sound whose copy was edited in place is dragged again.

### Can't be verified here (no Mac, no DAW)

- Every drop into Live 12 and Logic: AU, VST3, and CLAP where hosted.
- The no-sound hints in real use: Logic's in Logic, the other hosts' words in Live.
- A sound given up when the host stops running blocks mid-clip.
- How auditions sound.
- Live's auto-warp on the loops, especially FUT03's 6-bar riffs.
- Whether either DAW reads anything from the files beyond the audio.
- `#` handling.
- Writing `~/Music` from Logic's AU.
- Drags on Windows and Linux.

These become the v0.2 checklist in `docs/listening.md`:
- drag a one-shot to an audio track, a Drum Rack pad and a MIDI track (Simpler);
- drag a loop;
- in Logic, drag to an audio track and to Quick Sampler, and hear an audition while stopped with the track selected;
- a 44.1 kHz Logic project;
- names with `#`;
- Collect All and Save, and "Copy audio files into project";
- Standalone to Finder.

### Questions for you (each with the default I'd go with)

These were announced to you with their defaults, which the build follows; the defaults await your OK and can change until v0.2 ships.

1. **Dry samples now, "as heard in the kit" later?** The dry files are louder than in the groove and have none of the kit's Space, Echo or ducking.
   - **Default:** dry now. As-heard renders come with M6's audio export.
2. **File names keep the kit's own spelling.** Middle C is C4, and v1 and v2 are the soft and loud layers: `Chrome Pluck F#4 v2 - FUT01 134 F#m 11A.wav`. Live and Logic call that note F#3. Names can't change after release.
   - **Default:** keep the kit's spelling, so names match the kit's files and docs. The File box tooltip gives the DAW's note name.
3. **The Samples button opens the new browser.** The install panel moves behind its "Content…" button, and still opens by itself when a kit's samples are missing. Is that OK?
   - **Default:** yes.

## 9. Deliberately later

| Later | Why |
|---|---|
| "As heard in the kit" renders (Space, Echo, the kit's level), D1's Kit FX | Needs an offline Engine render on a worker, a WAV writer in the plugin and a render-before-drag UI. That is M6's audio export (question 1). |
| `smpl` root and loop points, and `acid` tempo chunks | No DAW is shown to need them; Logic's Sampler reading the header is the likely gain. They change the bytes, so they would need a new name or folder (v0.2 files never change). Decide after the Mac checks. |
| The pitch of FUT01's and FUT02's one-key accents (for example Rave Stab is F#3, but its key is 52) | It lives only in the recipes. It needs a kit.json field in a later content version, not a sidecar. |
| Multi-file drags (every layer and round robin, for Logic's Sampler or a Drum Rack) | One file per drag answers the ask. Multi-file drops are untested in both DAWs. |
| Favourites (the crate), tags, search | M6. About 35 sounds per kit need no search. |
| Auditions in time and in key with the groove | M6. Needs transport-aware starts and latency alignment (424 samples at 48 kHz). |
| An audition level control and a limiter | Polish. A fixed −6 dB under the Output knob is enough to choose sounds. |
| Repitch or time-stretch renders to the project's key and tempo | M5's "Change key" and Signalsmith. |
| Trimming lead-ins, padding end-aligned files to the grid | It changes the bytes; the hints cover it. |
| Showing the MIDI channel and key that play each sound in Wubansia | The A/B switches and Lane mode make a one-line answer misleading. |
| DAW checks on Windows and Linux | Your setup is Live and Logic on a Mac. CI still builds and tests all three OSes. |
